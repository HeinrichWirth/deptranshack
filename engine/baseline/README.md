## Запуск

Из корня проекта: `./COPY_MAIN/run.ps1 -RunName my_run -Count 1510`.

Режим «геометрия на каждом пятом кадре»: `./COPY_MAIN/run.ps1 -RunName my_every_fifth -Count 1510 -SolveStride 5 -SolveOffset 4`.
Это 5-й, 10-й, 15-й кадр по счёту (индексы 4, 9, 14). Чтение, сшивка и индексирование всех промежуточных кадров сохраняются; геометрия получает прежнюю полную доступную историю T−11…T. Поза T+1 разрешена, его облако запрещено. Прежние проверки движения и разрывов остаются. Без параметров режим прежний. Результаты первого полного замера этого режима — `results/EVERY_FIFTH/report.html`.

Исторический режим «вход 5 Гц, геометрия на каждом третьем»: `./COPY_MAIN/run.ps1 -RunName my_5hz -Count 1510 -InputStride 2 -SolveStride 3 -SolveOffset 2 -ImmediateDirection:$false`.
`Count` относится к исходному потоку: из 1510 кадров останутся 755 (исходные индексы 0, 2, 4…). Пропущенные payload не читаются и не сшиваются. Окно содержит до 12 оставленных кадров, до 2,2 с; разрешённая поза следующего оставленного кадра имеет исходный индекс T+2 и задержку около 200 мс. Внутренний frame/provenance.source_frame нумерует поток 5 Гц; исходные номера сохранены в source_frame_index, source_index_map.json и source_identity_map каждой summary. Это режим с изменёнными входными данными: точное совпадение со старыми прогнозами не предполагается. Проверка — `report_5hz.py`, отчёт — `results/INPUT5HZ_SOLVE3/report.html`.

Нужен существующий образ `deptrans-realtime:production`. Скрипт использует его библиотеки, но исполняет код из `COPY_MAIN/app`; копирует исходный DB3 внутрь нового контейнера; проверяет SHA256; выполняет причинный прогон. Диагностика пишется внутри Linux. По завершении измеряемого прогона результаты переносятся в `COPY_MAIN/results/my_run/results.tar.gz`, таблица времени — в `STAGES_MS.json`. `--rm` удаляет временный контейнер вместе с DB3 и временными результатами.

LAS не создаются. JSON/NPZ содержат прогнозы, исходные идентификаторы точек, позы, временные метки и результаты проверок. Перед новым прогоном задавайте новое имя. Для просмотра сохранённых JSON/NPZ можно распаковать архив или выполнить `python -B COPY_MAIN/verify_trial.py COPY_MAIN/results/my_run`; скрипт распакует его в `payload` и сравнит общие кадры с сохранённым исходным прогоном.

Конфигурация — `config.json`: 2 geometry workers × 2 native candidate threads; ICP query workers=1. Алгоритмические пороги, число ICP-итераций, разрешение вокселей, геометрия рельсов, causal window и допустимая задержка позы сохранены.

## Изменения

1. Выбор первого исходного измерения каждой 22-см ячейки: точное взаимно-однозначное целочисленное кодирование тройки координат вместо сортировки NumPy по трём столбцам. Сохраняются состав и порядок точек; вне допустимого диапазона используется исходная реализация. Это относится только к сшивке: облака детекторов не прореживаются дополнительно.
2. Диагностика пишется в Linux; перенос на Windows вынесен за время replay. Исходный replay писал множество небольших файлов через Windows bind mount.
3. В числовом контракте C4 уникальные округлённые точки считаются по точным целочисленным ключам; геометрия и итоговые количества сохранены.
4. STEP2 один раз считает характеристику расстояния между точками для обеих стартовых гипотез, переиспользуя то же дерево поиска.
5. Граница C4 smoothing / STEP6 измеряется прямыми таймерами вместо глобального Python line tracing. Численные операции не меняются.
6. Число потоков выбрано по причинному 400-кадровому прогону, а не только по времени одного ядра геометрии.

## Проверки и ограничения

`verify_voxel.py`: точные значения и порядок выбранных точек на 89 реальных кадрах, float32/float64, дубликатах, границах ячеек и пустом входе. `fixed_work_bench.py`: ровно 24 фиксированных геометрических задачи из всей записи, без пропусков scheduler; использует сохранённые причинные позы как фиксированную входную fixture, поэтому не является измерением live-регистрации. `verify_trial.py`: все новые позы, общие прогнозы, provenance, causality и hashes результата.

Полный replay заново вычисляет позы из raw; сохранённые позы используются только после него для проверки. Облака будущего запрещены; для T разрешена только поза T+1. Отказы регистрации не заполняются интерполяцией. Scheduler сохраняет правило latest pending; число задач между вариантами может отличаться, это явно отражается в отчёте.

Это симуляция последовательного ROS2 PointCloud2 из DB3, без отдельного DDS publisher/subscriber. При отставании reader сохраняет все кадры и измеряет backlog относительно исходных времён. Скорость DDS, потери реального транспорта и точность по независимому GT этим тестом не проверяются.

`setup_copy.py` — исторический одноразовый инструмент первоначального копирования; повторно запускать его поверх оптимизированной копии не нужно.
