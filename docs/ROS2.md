# Подключение к ROS 2

ROS 2 передаёт сообщения между программами через именованные топики. В нашем случае входной топик содержит `sensor_msgs/msg/PointCloud2`: координаты точек, интенсивность и метку времени. Адаптер подписывается на него и передаёт каждое принятое облако в тот же геометрический движок, который используется при загрузке DB3 через веб.

## Стенд Ubuntu 22.04 / ROS 2 Humble

Нужны Git и Docker с Compose. ROS 2 и зависимости адаптера устанавливаются внутри образа. Если на стенде уже запущен источник облаков, дополнительное проигрывание bag не требуется.

```bash
git clone https://github.com/HeinrichWirth/deptranshack.git
cd deptranshack
export CLOUD_TOPIC=/lidar_points
export ROS_DOMAIN_ID=0
docker compose -f compose.ros2.yaml -f compose.ros2.host.yaml up --build -d
docker compose -f compose.ros2.yaml -f compose.ros2.host.yaml logs -f ros
```

После сообщения `READY` адаптер готов принимать облака. Откройте **http://localhost:8870**: текущий ROS-прогон выбирается автоматически, срез обновляется по завершённым расчётам. Можно остановить слежение, выбрать кадр, открыть подробный просмотр и таблицу объектов. Если страница была открыта до подключения адаптера, обновите её.

`CLOUD_TOPIC` должен совпадать с названием топика на стенде, `ROS_DOMAIN_ID` — с доменом источника. Входные оси: вперёд −Y, вправо +X, вверх +Z, метры, лидар в центре поезда. Поля `x`, `y`, `z`, `intensity` обязательны. Автоматического преобразования TF нет. Имя `frame_id` и метка `header.stamp` сохраняются; нулевая метка времени не принимается.

Linux-вариант использует `network_mode: host` только для ROS-адаптера: это позволяет обнаружить ROS-узлы хоста через DDS. TCP-порт движка 8871 опубликован только на loopback. Он предназначен для локального адаптера, а не для публичной сети. Внутренний веб-сервис и движок остаются отдельными контейнерами.

## Проигрывание bag

На стенде с установленным ROS 2 в другом терминале:

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export FASTRTPS_DEFAULT_PROFILES_FILE="$PWD/ros2/fastdds.xml"
ros2 topic list -t
ros2 bag play /path/to/recording --rate 1
```

Папка записи содержит `metadata.yaml` и файлы bag. Можно также указать отдельный DB3: `ros2 bag play /path/to/file.db3 --storage sqlite3 --rate 1`. Не запускайте одновременно реальный лидар и проигрыватель на одном входном топике.

### Локальная проверка, включая Windows с Docker Desktop

В этом режиме источник и подписчик работают внутри Docker. Устанавливать ROS 2 на Windows не нужно. Запускайте команды из репозитория:

```bash
docker compose -f compose.ros2.yaml up --build -d
docker compose -f compose.ros2.yaml logs ros
docker compose -f compose.ros2.yaml cp /path/to/file.db3 ros:/bag/test.db3
docker compose -f compose.ros2.yaml exec ros bash -c 'source /opt/ros/humble/setup.bash && ros2 bag play /bag/test.db3 --storage sqlite3 --rate 1 --read-ahead-queue-size 20 --disable-keyboard-controls --delay 2'
```

В PowerShell вместо `/path/to/file.db3` укажите путь Windows в кавычках. Если обычная веб-демонстрация уже занимает порт 8870, задайте перед запуском `$env:RAIL_WEB_PORT='8872'` в PowerShell или `export RAIL_WEB_PORT=8872` в bash.

После завершения проигрывания остановите подписчика: он закроет вход и даст движку сохранить итоговую таблицу. Затем удалите только временную копию bag:

```bash
docker compose -f compose.ros2.yaml stop ros
docker compose -f compose.ros2.yaml run --rm --no-deps ros rm -f /bag/test.db3
```

Исходный файл на компьютере остаётся целым. Для следующего проезда выполните `docker compose -f compose.ros2.yaml start ros`. Новый сеанс получает отдельный ID и новую историю. `down` сохраняет результаты в volume; `down -v` удаляет их.

## Результат в ROS 2

Топик **`/rail_inspector/result`**, тип **`std_msgs/msg/String`**, содержит JSON. Прочитать его на Linux-стенде:

```bash
ros2 topic echo /rail_inspector/result std_msgs/msg/String
```

Для локального Docker-теста добавьте перед командой `docker compose -f compose.ros2.yaml exec ros bash -c 'source /opt/ros/humble/setup.bash && ...'`.

| Поле | Значение |
|---|---|
| `job`, `source_frame` | Сеанс и порядковый номер принятого ROS-сообщения |
| `header_time_ns`, `frame_id` | Исходные время измерения и система координат |
| `assessment_available` | Для этого пакета есть действительная проверка |
| `obstacle_detected` | Есть подтверждённый объект в текущем пакете; `null` при недоступной проверке |
| `distance_m` | Расстояние до ближайшего подтверждённого объекта в текущем пакете, либо `null` |
| `objects[].first_distance_m` | Расстояние при первой детекции группы, как в таблице |
| `objects[].current_distance_m` | Расстояние в текущем наблюдении |
| `horizon_m` | Конец принятого пути, дальше результат неизвестен |
| `algorithm_ms` | Время расчёта без экспорта диагностики |
| `stale` | С момента последнего завершения прошла секунда либо сеанс остановлен |

Сообщение относится к указанному исходному кадру, а не к текущему положению поезда. При недоступной или устаревшей проверке `obstacle_detected=null`: это не сообщение «путь свободен». Система не подключена к тормозам. После завершения сеанса полный отчёт остаётся в веб-просмотрщике.

## Буферы и причинность

Подписка: best effort, volatile, keep last 1. Она совместима с best-effort и reliable источниками. Между callback и отправителем хранится одно заменяемое облако; по TCP передаётся не более одного неподтверждённого пакета. Просроченное ожидание более 100 мс отбрасывается. Если передача заблокирована, старые облака не образуют очередь.

Профиль `ros2/fastdds.xml` увеличивает сегмент shared memory до 64 МиБ для облаков по несколько мегабайт. В локальном ROS-контейнере он применяется и к подписчику, и к `ros2 bag play`. На Linux-хосте экспортируйте его также для проигрывателя, как в примере выше; host-вариант разделяет IPC с хостом. UDP остаётся доступным для других машин. [Описание Fast DDS 2.6](https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/transport/shared_memory/shared_memory.html) предупреждает о потерях при слишком маленьком сегменте. Пропуски в best-effort потоке всё равно возможны, поэтому проверяйте счётчики и журнал.

CDR-адаптер и движок запускаются на одном Docker-хосте. Приёмник проверяет возраст пакета по общим монотонным часам, отбрасывает передачу дольше 100 мс и включает время передачи в исходный срок обработки. Подключение этого внутреннего TCP-протокола с другой машины не поддерживается.

Замороженные регистрация, STEP1, STEP2, C4, сглаживание, STEP6 и защита получают те же структуры shared memory. Входной адаптер не читает bag, сохранённые позы или будущие облака. Для направления допускается поза следующего реально полученного сообщения. Его точки не входят в геометрию кадра T. Отсутствующий следующий кадр не подменяется.

Планирование 3 Гц использует `header.stamp`, в отличие от DB3-воспроизведения по времени записи. Номера live-кадров — порядок callback, а не SQLite message ID. Пропуски, изменение `frame_id`, обратное время или разрыв от 150 мс начинают новую сессию геометрии. Не включайте `ros2 bag play --loop`, если хотите один непрерывный физический проезд.

Небольшой выходной наблюдатель сохраняет измерения трекера для текущей таблицы. Он не меняет компоненты и решения трекера. Полные индексы точек записывает исходный движок при завершении; во время проезда доступна таблица измерений без выделения точек выбранной группы.

## Среда и границы проверки

ROS-адаптер: Ubuntu 22.04, ROS 2 Humble, Python 3.10. Геометрический движок: прежний образ Python 3.12 / Debian Bookworm с теми же native-модулями и зависимостями. Docker Compose запускает их вместе на Linux-стенде; это не перенос замороженной численной среды на Python 3.10.

Локальное испытание DDS и `ros2 bag play` не заменяет проверку сетевых настроек и скорости на Intel i7-9700E организаторов. Если облака не приходят, сначала проверьте топик, домен, QoS и доступность DDS между источником и адаптером. Во время live-проезда не запускайте параллельно второй тяжёлый расчёт.
