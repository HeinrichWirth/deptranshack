# Архитектура Rail Inspector

Схемы отображаются прямо на GitHub. Первая показывает расчёт, вторая — состав запускаемого приложения. Подробности этапов и сопоставления объектов — в [описании метода](ARCHITECTURE.md), управление демонстрацией — в [WEB_GUIDE.md](WEB_GUIDE.md).

## От облака до объекта

```mermaid
flowchart TD
    BAG["ROS 2 DB3 · исходная запись"] --> READ["Подача PointCloud2 по времени записи"]
    READ --> REG["Последовательная регистрация облаков<br/>оценка перемещения лидара"]
    READ --> BUF["Кольцевой буфер исходных облаков"]
    REG --> POSE["Принятые позы и границы разрывов"]
    POSE --> INPUT["Сшивка причинного окна<br/>текущий T и разрешённые прошлые облака"]
    BUF --> INPUT
    DIR["Поза следующего исходного кадра T+1<br/>только для направления"] -.-> INPUT
    INPUT --> SCHEDULE["Полный расчёт запрашивается 3 раза в секунду<br/>промежуточные облака пополняют историю"]
    SCHEDULE --> STEP1["STEP1 · две головки ходовых рельсов<br/>независимый ближний поиск 0–8 м"]
    STEP1 --> STEP2["STEP2 · поиск контактного рельса<br/>относительно найденной пары"]
    STEP1 --> ADAPTER["RAW seed adapter<br/>STEP1 + сырые точки → 3D-опора"]
    STEP2 --> FOUND{"Результат поиска<br/>контактного рельса"}
    FOUND -->|"Принят"| C4["C4 · продолжение контактного рельса"]
    C4 --> SMOOTH["C4_SMOOTH · сглаживание"]
    SMOOTH --> STEP6["STEP6 · восстановление ходового пути"]
    ADAPTER --> STEP6
    FOUND -->|"NOT_FOUND / AMBIGUOUS"| FALLBACK["При наличии пригодного прошлого пути:<br/>его коррекция по нынешним ходовым рельсам"]
    HISTORY[("История принятых путей")] -.-> FALLBACK
    STEP1 -.-> FALLBACK
    STEP6 --> CHECK["Проверка совместимости пути<br/>с независимой ближней парой"]
    FALLBACK --> CHECK
    CHECK --> GUARD["Защита продолжения<br/>сохраняем только поддержанный участок"]
    GUARD --> PATH["Принятый путь<br/>при отказе дальнего — только доступный ближний"]
    PATH -.-> HISTORY
    PATH --> ENVELOPE["Виртуальный поезд 2,1 × 3 м<br/>проверка реальных точек внутри габарита"]
    INPUT --> ENVELOPE
    ENVELOPE --> COMPONENTS["Пространственные компоненты попаданий<br/>вес дальних точек снижается после 70 м"]
    COMPONENTS --> TRACKS["Сопоставление наблюдений по исходным точкам<br/>и их окрестностям в общей системе координат"]
    TRACKS --> GROUPS["Автоматическая группировка в радиусе 10 м<br/>неподвижные опоры, раздельные сессии поз"]

    CONFIRM --> TABLE["Таблица объектов · кадры · дальность · размеры<br/>CSV / JSON / ссылки на наблюдения"]

    ENVELOPE --> VIEW

    classDef input fill:#eaf2fb,stroke:#4073a4,color:#152e49;
    classDef geometry fill:#e5f4ed,stroke:#368768,color:#153b2d;
    classDef output fill:#fff0d9,stroke:#ad7928,color:#49330e;

    class STEP1,STEP2,ADAPTER,C4,SMOOTH,STEP6,CHECK,GUARD,PATH,FALLBACK geometry;
    class TABLE,VIEW,CONFIRM,GROUPS output;
```

**Что важно при чтении схемы:**

- Промежуточные облака не теряются намеренно ради частоты 3 Гц: они участвуют в регистрации и истории. При перегрузке ожидающий элемент заменяется более свежим, поэтому растущей FIFO-очереди нет. Это не гарантирует обработку каждого облака.
- T+1 нужен для направления. Его облако допускается в изолированный регистрационный probe, но **не передаётся геометрическим детекторам**. В их входе нет будущих облаков, карты-эталона или class1/class2.
- Коррекция прошлого пути по ходовым — запасная ветка при `NOT_FOUND` / `AMBIGUOUS`, а не дополнительная правка поверх успешно принятой контактной геометрии.
- Если регистрация, опора или продолжение не приняты, дальний участок может отсутствовать. Его отсутствие означает «неизвестно», а не «путь свободен».
- Группировка 10 м меняет только представление объектов после геометрии. Она не двигает рельсы и не меняет список точек-попаданий. Разные близкие предметы могут объединиться.

## Что запускает Docker

```mermaid
flowchart LR
    USER["Пользователь<br/>браузер localhost:8870"]
    FILE["Файл DB3 на компьютере"]
    subgraph DOCKER["Docker Compose · один сервис inspector"]
        WEB["HTTP-сервер и веб-интерфейс<br/>app/ + web/"]
        JOBS["Управление прогоном<br/>загрузка · выбор топика · запуск"]
        RUNTIME["Принятый runtime<br/>регистрация · scheduler · защита · трекер"]
        ENGINE["Замороженные геометрические этапы<br/>Python + native C++"]
        RESULTS["Чтение результатов<br/>срез · группировка · таблица · экспорт"]
        WEB --> JOBS
        JOBS --> RUNTIME
        RUNTIME --> ENGINE
        ENGINE --> RUNTIME
        RESULTS --> WEB
    end
    subgraph DATA["Постоянный Docker volume rail-data"]
        TEMP["Временная копия DB3<br/>удаляется после попытки расчёта"]
        SAVED["Результат прогона<br/>облака · пути · точки · треки · журналы"]
    end
    FILE -->|"Загрузка через браузер"| WEB
    USER <-->|"Управление и просмотр"| WEB
    JOBS --> TEMP
    TEMP --> RUNTIME
    RUNTIME --> SAVED
    SAVED --> RESULTS
```

Временная копия входа читается из файловой системы Docker. Исходный файл пользователя остаётся неизменным. Сохранённые результаты переживают закрытие вкладки и обычный `docker compose down` без `-v`.

Это воспроизведение ROS 2 записи по timestamps, а не подписка на живой DDS. Веб-просмотрщик читает готовые результаты и не влияет на inference. Полный путь к реализации каждого блока приведён в [ARCHITECTURE.md](ARCHITECTURE.md#папки).
