# Как устроен расчёт

## Поток данных

```
DB3 → CDR PointCloud2 → кольцевой буфер исходных облаков
                          ↓
                    регистрация 10 Гц
                          ↓
              T + поза T+1 для направления
                          ↓
      STEP1 → STEP2 → C4 → сглаживание → STEP6
                          ↓
            выбор пути / коррекция по ближним
                          ↓
               защита продолжения → габарит
                          ↓
              компоненты → треки → файлы
                          ↓
              веб-срез / таблица / просмотр
```

Веб-приложение читает результаты. Оно не подаёт свою геометрию, разметку или будущие облака обратно в inference.

## Папки

| Путь | Назначение |
|---|---|
| `app/jobs.py` | загрузка, выбор топика, один активный прогон, запуск worker, удаление временного входа |
| `app/results.py` | чтение результата и проекция для отображения |
| `app/grouping.py` | автоматические объекты по фиксированным пространственным окнам 10 м |
| `app/server.py` | небольшой HTTP API и раздача локального интерфейса |
| `app/storage.py` | атомарные JSON-записи и чтение журналов |
| `web/` | экран загрузки, срез и таблица; обычные HTML/CSS/JS, без CDN |
| `web/viewer/` | подробный просмотрщик замороженного прогноза |
| `engine/runtime/` | принятый scheduler, регистрация, подготовка, защита, трекер |
| `engine/baseline/` | исходники зафиксированных геометрических этапов |
| `native/` | исходники C++ модулей; сборка со строгой арифметикой без fast-math |
| `engine/SOURCE_MANIFEST.json` | SHA-256 исходников принятого движка |
| `scripts/seal_build.py` | проверка исходников и фиксация контрольных сумм новых бинарников |

Research-код намеренно сохранён без косметического переписывания: это облегчает доказательство неизменности результата. Читаемая оболочка, интерфейс и документация находятся отдельно. Чтобы поменять алгоритм, сначала создайте новую версию и парную проверку на одинаковых входах; не просто обновляйте хэши после правки.

## Геометрические этапы

1. **STEP1:** обнаруживает две головки ходовых рельсов в текущем облаке, ближние 0–8 м. Не использует прогноз траектории как источник ответа.
2. **STEP2:** ищет контактный рельс относительно ходовых; принятый F4-NU robust direct detector. Параметры и шаблон включены в baseline.
3. **C4:** продолжает контактный рельс по текущему и разрешённым предыдущим сырым облакам. Локальные пространственные индексы переиспользуются, результат поиска каждого полного цикла вычисляется заново.
4. **C4_SMOOTH / STEP6:** сглаживание контактного пути и восстановление двух ходовых рельсов. RAW seed adapter строит 3D seed из STEP1 и сырых точек, без class1/class2.
5. **Выбор пути:** подгонка прошлого пути по текущим ходовым разрешена при `NOT_FOUND` или `AMBIGUOUS` от завершённого STEP2. Она не выполняется поверх успешно принятой контактной геометрии. Независимые ближние рельсы проверяют совместимость пути.
6. **Продолжение и защита:** исходное линейное продолжение до +20 м можно использовать только до первого неподтверждённого участка. В 2-метровых секциях должны поддерживаться обе головки: минимум 3 точки, 3 разные ячейки 3 см, продольный размах 0,5 м; допуски ±5,5 см поперёк и ±3 см по высоте. Принятые исходные рельсы не перемещаются.
7. **Габарит:** 2,1 × 3 м от головок. Проникновение строго больше 10 см снизу, 3 см по бокам и сверху. Вес дальней точки — `min(1, (70/r)^2)`. Минимальная сумма весов компоненты — 3.

## Почему один предмет мог получить два ID

В одном пакете точки объединяются через 5-см воксели и связность с радиусом 24 см. Компоненте нужны минимум 3 точки и 2 вокселя. Раздельные видимые части одного предмета могут стать разными компонентами.

Между пакетами компоненту переводят в общую систему координат принятой позой. Сопоставление ищет расстояния до сохранённой опоры трека: радиус 35 см, доля совпадений минимум 20% хотя бы в одном направлении, перерыв максимум 3 с. Выбирается наименьшая оценка расстояния с поправкой на долю совпадений. В одной сессии используется до 12 000 опорных вокселей трека; точная принадлежность исходным точкам сохраняется отдельно.

Важная особенность: активные треки выбираются **до** обработки текущих компонент. Две новые части в одном первом пакете поэтому получают два ID. Уже существующие разные ID автоматически не сливаются. Несколько текущих частей могут присоединиться к одному старому ID, если он уже был.

Именно поэтому пользователь указал, что группы 3/4 и 10/11 на принятом прогоне — одни и те же предметы. Это ограничение исходной ассоциации, не два дополнительных физических препятствия.

В конечной таблице добавлено разрешённое пользователем грубое автоматическое объединение. Наблюдения обходятся по исходному времени. Первое наблюдение создаёт неподвижную опору в мировых координатах; следующее присоединяется к ближайшей опоре в радиусе 10 м в той же сессии регистрации. Опоры не сдвигаются и не объединяются цепочкой — иначе последовательность близких точек могла бы склеить весь тоннель. Отдельные препятствия ближе 10 м намеренно могут стать одной группой.

Подтверждение группы требует двух **разных исходных пакетов**. Две части одного кадра не дают второго подтверждения. Никаких ID, расстояний до ожидаемых синтетических предметов или GT в правиле нет. Оно работает с позициями обнаружений, а не с меняющимся расстоянием до текущего лидара. Габарит, исходные компоненты и `tracks.json` остаются неизменными. Размер строки берётся из наиболее плотного наблюдения, а не складывается из размеров фрагментов: это размер видимой части, не восстановленная полная форма. В JSON остаются исходные `member_ids` и точные наблюдения.

## Время и отсутствие очереди

Reader подаёт сообщения по timestamps записи. Регистрация получает последние доступные сообщения; канал содержит один заменяемый ожидающий элемент. Растущего FIFO нет. При перегрузке старые сообщения заменяются или отклоняются по deadline; это видно в журналах и не выдаётся за обработку всех кадров.

Полный расчёт планируется с частотой 3 Гц. Промежуточные облака нужны для сшивки и истории. Для направления допускается поза T+1: изолированный регистрационный probe читает это облако, но геометрический worker получает только позу. Облако T+1 в детекторы не входит.

`total_ms` — подготовка, геометрия, защита, габарит, трекер и запись результата внутри geometry worker. `age_ms` дополнительно включает ожидание и регистрацию перед запуском. Фактическая частота завершений может быть ниже 3 Гц.

## Результаты и API

Каждый запуск: `/data/jobs/<uuid>/`. `job.json` описывает вход и состояние; `result/` содержит `input.jsonl`, `registration.jsonl`, `geometry.jsonl`, `far.jsonl`, `tracks.json`, `COMPLETE.json`, точные `batches/*.npz` и `rail_refresh/*.npz`. Исходные ID точек хранятся в `owners`: `(source_frame, source_point_index)`. Файл bag временный и удаляется после попытки расчёта.

| Метод | URL | Смысл |
|---|---|---|
| PUT | `/api/upload` | тело — байты DB3, `X-Filename` — URL-encoded имя |
| POST | `/api/start` | JSON `{job, topic}` |
| GET | `/api/status?job=…` | состояние, кадры, последнее измерение времени |
| GET | `/api/slice?job=…&source=…&distance=8` | срез для отображения |
| GET | `/api/objects?job=…` | автоматические пространственные группы и исходные ID |
| GET | `/api/export?job=…&format=csv` | таблица; без `format` — JSON |
| GET | `/api/log?job=…` | последние 100 КБ журнала worker |

Срез на главном экране — диагностическая проекция. Его счётчик красных точек не является счётчиком подтверждённых объектов. Для быстрого отображения рисуется до 20 000 точек среза; расчёт не прореживается. Подробный просмотрщик получает полный сохранённый пакет.
