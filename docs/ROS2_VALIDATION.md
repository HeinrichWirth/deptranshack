# Проверка живого ROS 2 входа · 29 сентября 2026

Проверена цепочка `ros2 bag play → DDS PointCloud2 → CDR-адаптер → замороженный движок → ROS-результат и веб-срез`. Приёмник не имел доступа к исходному bag: файл находился только в volume проигрывателя. Сверка с исходником выполнялась после завершения inference.

## Условия

- Полная синтетическая запись `cloud_with_fake_obj_0.db3`, 1510 сообщений `/lidar_points`, около 151 секунды, воспроизведение `--rate 1`.
- AMD Ryzen 9 7950X3D, Docker Desktop / WSL2 Linux 6.6.87.2, 32 логических CPU. Это не компьютер заказчика Intel i7-9700E.
- ROS-образ Humble / Ubuntu 22.04, `rmw_fastrtps_cpp`, best effort, keep last 1. Профиль Fast DDS с сегментом shared memory 64 МиБ, `/dev/shm` контейнера 512 МиБ.
- Планирование полного расчёта 3 Гц по `header.stamp`, прежние геометрия, параметры и защита. Экспорт live-таблицы выполнялся в отдельном потоке с одним заменяемым снимком.
- Во время прогона работали веб-демонстрация и независимый ROS-подписчик результатов.

Не пришло исходное сообщение с порядковым индексом **1** (второе в записи). Остальные приняты в исходном порядке. Этот разрыв отмечен по меткам времени, история регистрации начинается заново. Мы не заявляем доставку каждого сообщения в best-effort режиме.

У адаптера 0 замен ожидающего облака и 0 просроченных отправок. Внутри замороженной регистрации 36 ожидающих запросов заменены свежими; у очереди геометрии замен 0. Каналы ограничены одним ожидающим элементом: растущей очереди догоняющего расчёта нет. Это не означает, что каждый входной кадр проходит все этапы.

Первое подтверждённое обнаружение, полученное внешним подписчиком: live-кадр 139, дальность в этом наблюдении **66,61 м**. Первое наблюдение той же группы — live-кадр 133, **69,34 м**. Номера live-кадров не равны SQLite ID: они отсчитываются по полученным callback.

Одинаковое число групп с DB3-прогоном не доказывает побайтное совпадение всех предсказаний: при живом расписании набор принятых историй отличается. Сами замороженные исходники и конфигурация не изменились; проверка контрольных сумм 416 файлов проходит.

## Скорость

Чистый расчёт: `total_ms − export_ms`. В него входят подготовка, геометрия, проверка габарита и трекер. Сохранение промежуточной таблицы вынесено из этого потока.

| Метрика | Время |
|---|---:|
| Медиана алгоритма | **263,85 мс** |
| p95 алгоритма | **328,21 мс** |

| Callback → начало отправки, p95 | 1,96 мс |

Последние два числа измеряют только работу адаптера после получения ROS-callback, а не весь DDS-транспорт. Полный протокол, счётчики и времена отдельных этапов находятся в [ros2_qualification.json](ros2_qualification.json).

357 завершённых расчётов за примерно 151 секунду — около **2,37 Гц** фактически, при запросе 3 Гц. Медиана и p95 укладываются в интервал 333 мс, максимум превышает его. Гарантии жёсткого реального времени на стенде заказчика этот тест не даёт.

## Что исправили при интеграции

Первый DDS-тест со стандартным размером shared memory принял 1477 из 1510 облаков. Увеличение сегмента для 4,9-МБ сообщений сократило потери до одного входного кадра в двух последующих полных запусках. Это транспортная настройка, не изменение детектора.

Синхронное сохранение промежуточной таблицы давало медиану алгоритма 304 мс и p95 390 мс. После отделения записи в ограниченный выходной поток получили 264 и 328 мс. Таблица по-прежнему использует те же наблюдения трекера; итоговые индексы точек сохраняет исходный движок.

## Дополнительные проверки

- 11 unit-проверок: прежние контракты движка, точная передача CDR, предел размера пакета, обрыв соединения, устаревший ответ и запрет подтверждения ещё не завершённым пакетом.
- Браузер: таблица, выбор кадра, подробный просмотр, движение по прогнозу; ошибок JavaScript нет.
- После окончания потока приходит недоступная проверка, а не «путь свободен».
- Повторное подключение создаёт новый сеанс. `docker stop` завершает подписчика и сохраняет результат.
- Временная копия DB3 в Docker удалена после сверки. Сохранённые результаты остаются доступны для просмотра.

Запуск и диагностика подключения — в [ROS2.md](ROS2.md). Проверка host-network/DDS на физическом Ubuntu-стенде организаторов и работа на неизвестном bag остаются отдельными испытаниями.

## Запись демонстрации от запуска ROS 2

[Видео, 3 минуты 2 секунды](../presentation/HW_ROS2_live.webm): запуск подписчика, проверка топиков, `ros2 bag play --rate 1`, живой срез и таблица, затем сохранённый путь сверху. Вступление выводит команды и их фактический вывод; ускорения воспроизведения нет. Контейнеры и временная копия bag подготовлены до начала записи.

Для записи выполнен отдельный полный прогон `253cfae8e9f342e5955f457394248ae6`: 1509 входных облаков, 334 завершённых расчёта, 9 подтверждённых групп в таблице. Медиана чистого расчёта — 262,6 мс, p95 — 335,6 мс, максимум — 387,3 мс. Во время прогона одновременно записывался экран. Получилось около 2,21 завершённых расчёта в секунду при запросе 3 Гц. Регистрация заменила 53 ожидающих запроса свежими; очередь геометрии — 0. Временная копия bag удалена после завершения.

В просмотрщике исправлена ориентация вида сверху: продольная ось направлена вверх, поперечная совпадает со срезом. Изменены только отрисовка и её проверка, исходники геометрического движка сохранены. Прошли 11 тестов Python, тест ориентации на четырёх направлениях и браузерная проверка таблицы, выбора кадра и проезда.
