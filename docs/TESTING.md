# Проверить сборку и результат

## Без внешних данных

```sh
docker compose up --build -d
docker compose exec inspector python -m unittest discover -s tests -v
```

Проверяются SHA-256 принятого Python-кода, точность 3D арифметики, отсечение неподдержанного хвоста, подтверждение в разных исходных кадрах и автоматическая группировка: без изменения исходных наблюдений, склейки цепочкой и перехода между сессиями позы.

Docker сам собирает шесть native-модулей. Прежние локальные образы `deptrans-*` и файлы `.so` в репозитории не нужны. Сборка останавливается при нарушении `engine/SOURCE_MANIFEST.json`.

## С собственным DB3

Основной тест — тот же путь, которым пользуется человек: загрузить файл в браузере, нажать «Начать расчёт», увидеть первые срезы до завершения всей записи, затем открыть объект и проехать по сохранённому прогнозу.

Если установлен Python на компьютере, это можно повторить автоматически:

```sh
python tests/full_http.py --bag /path/to/recording.db3
```

На Windows вместо `/path/to/recording.db3` укажите путь в кавычках. Проверка использует стандартную библиотеку Python. Она загружает **весь** файл, запускает первый доступный PointCloud2 topic, получает живой срез, ждёт завершения и проверяет число полученных кадров и удаление временного входа. Отчёт — `local-results/http-test.json`.

Проверка браузера — дополнительная, для разработчика. `tests/ui.cjs` использует Playwright, открывает готовый прогон, таблицу, выбранный кадр и проверяет шаг виртуального поезда. Нужны Node, Playwright и браузер; для самого приложения они не нужны. Переменные `PLAYWRIGHT_MODULE`, `BROWSER_CHANNEL` и `RAIL_URL` позволяют использовать существующую установку.

## Парная проверка геометрии

`tests/fingerprint_geometry.py` запускается в **двух отдельных процессах**, сначала с принятым движком, затем с движком собранного образа. Он получает одни и те же сырые облака и сохранённые причинные позы. Хэшируются все ndarray предсказания, covariance, C4, provenance и ближний поиск; время не входит в сравнение.

Параметры:

```
--engine /path/to/engine
--previous /path/to/previous/payload
--bag /path/to/recording.db3
--out /path/to/fingerprints.json
```

`previous` содержит метаданные прежних causal-пакетов, `registration.jsonl` и `input.jsonl`. Для направления в обоих процессах берётся одинаковая принятая поза T+1, а не облако. Это проверка численной эквивалентности, не скоростной онлайн-тест. Сырые данные и эталоны не включены в Git.

## Почему два полных запуска не обязаны дать одинаковую таблицу

Режим подачи привязан к часам. Просроченные кадры регистрации пропускаются, поэтому загрузка CPU может изменить принятую историю и подтверждения объектов. Сравнение геометрии выполняется на одинаковых сохранённых входах; полные запуски отдельно проверяют работу потока и формирование результатов.

Отдельно проверяются:

1. Неизменность кода и параметров.
2. Совпадение геометрии на одинаковых входах, включая пересобранный C++.
3. Полный путь через веб и Docker с реальной подачей по timestamps.
4. Сохранение исходных точек, входных ID, отображаемых кадров и воспроизводимость автоматических групп.

Измерения упаковочного прогона и итоговая квалификация записаны в `RELEASE_VALIDATION.md`.
