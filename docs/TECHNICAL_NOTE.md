# Метод обнаружения препятствий

Rail Inspector проверяет, пересекают ли реальные точки лидара габарит движения поезда. Метод использует геометрию рельсов и повторяемость наблюдений. Обучение классификатора на примерах отдельных типов препятствий не требуется.

Заказчик: Московский транспорт, Департамент транспорта и развития дорожно-транспортной инфраструктуры. Кейс 5 ЛЦТ2026: обнаружение посторонних объектов для беспилотных поездов в тоннеле метро по данным 3D-лидара.

## Стек

Python 3.12 управляет потоком и обработкой результатов. Вычислительные участки реализованы на C++ с pybind11 и OpenMP. NumPy и SciPy используются для работы с массивами и геометрией. SQLite обеспечивает чтение DB3. Веб-приложение использует стандартный HTTP-сервер Python и JavaScript/Canvas, без внешнего CDN. Docker собирает зависимости и native-модули. GPU в текущем расчёте не используется.

## Вход и координаты

Вход MVP — SQLite DB3 с сообщениями PointCloud2 в CDR1. Нужны поля x, y, z, intensity. Единицы — метры, оси испытанной записи: вперёд −Y, вправо +X, вверх +Z. Положение лидара соответствует центру поезда. Перед запуском на другом датчике требуется проверить эти соглашения.

Последовательная регистрация оценивает преобразование каждого облака в общую систему координат. Для точки p_i из кадра i преобразование в координаты текущего кадра T имеет вид:

`p_T = inverse(H_T) · H_i · p_i`, где H — однородное преобразование 4 × 4.

Окно содержит текущий и принятые прошлые кадры. Разрывы регистрации не заполняются искусственными позами. Для направления используется поза следующего исходного кадра T+1, полученная отдельной регистрацией. Его точки в детекторы не поступают. Связь каждой точки с исходной записью сохраняется как `(source_frame, source_point_index)`.

## Поиск пути

STEP1 независимо ищет две головки ходовых рельсов на первых 0–8 м. STEP2 использует найденную пару для поиска контактного рельса. C4 продолжает контактный профиль, C4_SMOOTH сглаживает его, STEP6 восстанавливает ходовой путь. Начальную 3D-опору строит адаптер из STEP1 и сырых точек. Метки классов LAS в расчёте не используются.

Если STEP2 завершился с `NOT_FOUND` или `AMBIGUOUS`, пригодный прошлый путь корректируется по нынешним ходовым рельсам. Успешно принятую контактную геометрию эта ветка не заменяет. Независимая ближняя пара проверяет согласованность результата.

Продолжение проходит проверку поддержки обеих головок реальными точками. На первом неподдержанном участке дальний хвост отсекается. При недостатке данных остаётся доступный ближний путь. За его концом состояние неизвестно.

## Проверка габарита

Для каждой позиции вдоль пути строится локальный поперечный базис. Центр — середина пары головок, боковая ось определяется парой, продольная — направлением пути. Координаты точки в этом базисе обозначим u поперёк и h по высоте от головок.

Габарит имеет ширину W = 2,1 м и высоту H = 3 м. Точка считается попаданием, когда находится внутри продольного проверяемого участка и выполняются строгие неравенства:

`|u| < W/2 − m_side`, `m_bottom < h < H − m_top`.

Параметры: m_bottom = 0,10 м, m_side = m_top = 0,03 м. Это внутренние параметры расчёта, в пользовательском интерфейсе они не регулируются.

Дальность точки r измеряется по прямой от исходного лидара. Вес равен 1 до 70 м и `(70/r)²` после 70 м. Компоненте нужна сумма весов не менее 3. Это снижает вклад редких дальних попаданий.

## Объекты и выход

Точки-попадания образуют пространственные компоненты. Исходный трекер сохраняет связь наблюдений и точек между пакетами. Итоговые группы формируются по неподвижным опорам в радиусе 10 м, раздельно для каждой сессии регистрации. Второй независимый исходный пакет переводит группу в `CONFIRMED`.

Выход содержит ID группы, кадры наблюдений, минимальную дальность, ширину, высоту и площадь охватывающего прямоугольника видимой части. Для размеров выбирается наиболее плотное наблюдение. Форматы экспорта — CSV и JSON. Веб-интерфейс открывает соответствующие кадры и поперечные срезы.

Подтверждение означает повторное наблюдение, а не эталонную оценку опасности. Два близких физических предмета могут объединиться в одну группу. При отказе геометрии отсутствие обнаружения нельзя трактовать как свободный путь.

## Параметры и воспроизводимость

| Параметр | Значение в MVP | Где задан |
|---|---|---|
| Частота запроса полного расчёта | 3 Гц | `engine/config.json` |
| История облаков | до 12 причинных кадров | `engine/config.json` |
| Ближний поиск | 0–8 м | `engine/config.json` |
| Габарит | 2,1 × 3 м | `engine/config.json` |
| Снижение веса дальних точек | после 70 м | `engine/config.json` |
| Защита продолжения | поддержка обеих головок по секциям | `engine/runtime/extension_guard.py` |
| Радиус итоговой группы | 10 м | `app/grouping.py` |
| Подтверждение | два разных пакета | `app/grouping.py` |

Параметры геометрии зафиксированы контрольными суммами. Их изменение создаёт новую версию метода и требует повторной проверки. Для обычного запуска редактирование конфигурации не требуется.

## Предварительный проезд и карта

Текущий MVP восстанавливает путь без карты предварительного проезда. Это увеличивает объём геометрического поиска и ограничивает дальность при перекрытиях.

Вариант развития — заранее построить карту рельсов и тоннеля, локализовать текущий кадр на этой карте и проверять новые точки относительно известного габарита. Повторный поиск рельсов можно сократить, оставив его для проверки и восстановления локализации.

Такой режим пока не реализован. Нужно измерить время и погрешность локализации, устойчивость в однотипном тоннеле, влияние изменений инфраструктуры и рассогласования карты. Дальность будет зависеть от плотности и видимости точек, точности позы и актуальности карты, поэтому ограничение только дальностью лидара пока не подтверждено.
